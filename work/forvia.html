FORVIA / 2023—25Data UX / Design leadership / Palantir Foundry

One system for complex decisions.

Leading the process, people, and system behind clearer industrial decision-making across FORVIA's Palantir ecosystem.

Lead UX research & design / Public case-study material only

01 / Why it mattered

Valuable data.
Fragmented rules.

FORVIA teams were using Palantir applications for manufacturing and business decisions, but different modules could introduce different layout logic, hierarchy, components, and scanning patterns.

The goal was a shared operational grammar: make dense industrial information easier to read while giving product teams a reusable system for future landing pages, dashboards, and workshop tools.

I led the work across audit, process definition, designer critique, stakeholder alignment and R&D workshops. The focus was a consistent product experience and a reusable system for application teams.

02 / The system

A shared
operational grammar.

The design system documents the interface from foundations upward: FORVIA palette, web landmarks, headers, navigation, card structures, filters, metrics, tabs, tables, charts, and action patterns.

Templates carry those rules into complete landing pages and data-heavy dashboards so a team can see how components behave in context, not only as isolated library pieces.

03 / Documentation model

From tokens to
working products.

The documentation is organized to answer four practical questions: what visual rules govern the product, how pages are structured, which components teams can reuse, and what the system looks like inside a live operational application.

01 / Foundations

Palette and navigation

A defined white, blue, sky-blue, dark-grey, and light-grey palette creates a controlled base for navigation and data emphasis.

02 / Structure

Landmarks before decoration

Banner, header, main content, cards, side filters, and dashboard regions establish predictable reading and interaction zones.

03 / Components

Reusable controls at scale

More than 30 documented buttons, tabs, metric cards, actions, and information patterns form a common interface vocabulary.

04 / Application

SAMBA as system proof

Matching, weight, and part-composition dashboards demonstrate the library against real analytics and industrial decision flows.

04 / Deliverable

Consistency is a
product capability.

The deliverable creates one source of truth across foundations, components, structural patterns, and complete page templates. Designers and developers can evaluate new screens against a documented system rather than reinventing the interface each time.

In enterprise software, consistency is operational: the system makes dense applications more predictable and gives future modules a clear place to start.

The result was not only a component library. It was a shared design process: a way for designers, developers, product owners, and R&D stakeholders to discuss quality using the same language.

05 / Discovery & alignment

Make complexity discussable.

Audit the experience across modules

The starting issue was inconsistency between applications using related data. An interface audit looks beyond colour and typography: where navigation sits, how filters affect results, how metrics are grouped and where actions appear. These structural differences matter because users repeatedly switch between operational contexts.

Connect design with domain knowledge

Stakeholder alignment and R&D workshops provided a setting for discussing industrial workflows and the information people need to interpret. My role connected that domain knowledge with design critique and process definition. The goal was a shared way to evaluate the interface, with product owners and designers working from the same problem.

Define what should stay consistent

Not every dashboard needs an identical layout. Navigation, component behaviour and feedback should be predictable, while the main content should reflect the task. The system gives teams a common starting point without flattening meaningful differences between matching, weight analysis and part composition.

06 / Design decisions

A library needs working examples.

From foundations to task structure

The documented palette and page landmarks establish a stable visual hierarchy. Headers orient the user; navigation identifies the current area; cards and tables organise information; filters narrow the working context. The system connects these elements so teams can compose a complete page instead of choosing disconnected components.

Use SAMBA to expose the real constraints

The SAMBA examples show how the system works with matching, weight and part-composition data. These screens are important because dense information exposes problems that a component specimen can hide: competing emphasis, crowded controls or an unclear relationship between summary and detail. Application examples make those relationships visible.

Keep actions and information distinct

A metric describes a condition; a filter changes the scope; an action changes something in the workflow. Giving each a consistent visual and positional treatment helps explain what a user can read, adjust or do. That distinction is especially valuable when the screen contains multiple charts and tables.

07 / Delivery & evolution

Maintain the system as a product.

What was delivered

The case documents foundations, more than 30 interface patterns, structural guidance and complete application examples. It also reflects design-process leadership: critique, stakeholder alignment and a common language for discussing interface quality. Public screenshots illustrate that scope without exposing private operational data.

What the evidence does not establish

A documented system is an enabling deliverable. It does not by itself prove faster decisions, fewer user errors or adoption across every application. Those outcomes need a baseline and evidence from actual use; they are not presented here as measured results.

Next actions for system governance

Track which patterns teams reuse and where they create exceptions. Review new requests against existing components, document the reason for additions and check the impact across page templates. For user validation, compare task completion and comprehension on representative workflows before expanding the library further.
